## Summary

NextAuth.js v5 (`next-auth@beta`, currently `5.0.0-beta.31`) is the correct package for Next.js 14 App Router. The tag `next-auth@5` does not exist on the registry — only `next-auth@beta` resolves to v5. The package has been in beta since 2023 and is production-ready for App Router projects, but the `@beta` tag is the only install path.

When using Prisma adapter with JWT session strategy, the `Session` table is not required in the database schema. The adapter uses the `Account` and `User` tables for OAuth account linking; JWT tokens live client-side. The existing Prisma 7 setup (custom output path `app/generated/prisma`, `PrismaPg` adapter from `@prisma/adapter-pg`) is fully compatible with `@auth/prisma-adapter` — the key is passing the existing `prisma` singleton (which already handles the Pg adapter connection) directly to `PrismaAdapter()`.

The most critical production gotcha for Railway: `AUTH_TRUST_HOST=true` must be set. Railway runs behind a reverse proxy and NextAuth v5 will reject requests where the `X-Forwarded-Host` header doesn't match the inferred host unless this flag is set. `AUTH_URL` / `NEXTAUTH_URL` is optional in v5 (host inferred from request headers), but `AUTH_SECRET` (or `NEXTAUTH_SECRET`) is mandatory.

**Primary recommendation:** Install `next-auth@beta @auth/prisma-adapter bcryptjs`, configure JWT + Credentials + Google with the edge-compatible split pattern (`auth.config.ts` + `auth.ts`), protect all routes via `middleware.ts` with explicit carve-outs for `/api/mcp` and `/api/auth`.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Session storage | Client (JWT cookie) | — | JWT strategy; no DB session rows needed |

| Password hashing | API/Backend (`auth.ts` authorize) | — | bcryptjs runs server-side only; never in browser |

| SessionProvider | Browser/Client (`components/Providers.tsx`) | Frontend Server (layout.tsx) | Provider must be 'use client'; layout.tsx wraps it |

### Pattern 1: Edge-Compatible Config Split

NextAuth v5 middleware runs in the Next.js Edge runtime. Prisma (with `@prisma/adapter-pg`) is NOT edge-compatible. The split pattern separates providers (edge-safe) from the full config (Node.js).

```typescript
// app/lib/auth.config.ts — edge-compatible, no Prisma import
// Source: https://authjs.dev/getting-started/migrating-to-v5#edge-compatibility
import Credentials from 'next-auth/providers/credentials'
import Google from 'next-auth/providers/google'
import type { NextAuthConfig } from 'next-auth'

export default {
  providers: [
    Google,
    Credentials({
      credentials: { email: {}, password: {} },
      // authorize is intentionally minimal here — full logic in auth.ts
      authorize: async () => null,
    }),
  ],
  pages: { signIn: '/sign-in' },
} satisfies NextAuthConfig
```

```typescript
// app/lib/auth.ts — full config with Prisma, only imported in Node.js contexts
// Source: https://authjs.dev/getting-started/migrating-to-v5#edge-compatibility
import NextAuth from 'next-auth'
import { PrismaAdapter } from '@auth/prisma-adapter'
import Credentials from 'next-auth/providers/credentials'
import Google from 'next-auth/providers/google'
import bcryptjs from 'bcryptjs'
import { prisma } from '@/app/lib/prisma'
import authConfig from './auth.config'

export const { handlers, signIn, signOut, auth } = NextAuth({
  ...authConfig,
  adapter: PrismaAdapter(prisma),
  session: { strategy: 'jwt' },
  providers: [
    Google,
    Credentials({
      credentials: { email: {}, password: {} },
      async authorize(credentials) {
        if (!credentials?.email || !credentials?.password) return null
        const user = await prisma.user.findUnique({
          where: { email: credentials.email as string },
        })
        if (!user?.password) return null
        const valid = await bcryptjs.compare(
          credentials.password as string,
          user.password
        )
        if (!valid) return null
        return { id: user.id, email: user.email, name: user.name }
      },
    }),
  ],
  callbacks: {
    jwt({ token, user }) {
      if (user?.id) token.id = user.id
      return token
    },
    session({ session, token }) {
      if (token.id) session.user.id = token.id as string
      return session
    },
  },
})
```

### Pattern 2: Middleware with Selective Exemption

```typescript
// middleware.ts — imports from auth.config.ts (edge-safe), NOT auth.ts
// Source: https://authjs.dev/reference/nextjs#middleware
import NextAuth from 'next-auth'
import authConfig from '@/app/lib/auth.config'

const { auth } = NextAuth(authConfig)

export default auth((req) => {
  const { pathname } = req.nextUrl
  const isLoggedIn = !!req.auth

  // Exempt: MCP (called by Claude Desktop, no auth headers), NextAuth internals
  if (
    pathname.startsWith('/api/mcp') ||
    pathname.startsWith('/api/auth')
  ) {
    return
  }

  // Protect all app routes
  if (!isLoggedIn && !pathname.startsWith('/sign-in') && !pathname.startsWith('/sign-up')) {
    return Response.redirect(new URL('/sign-in', req.nextUrl.origin))
  }

  // Prevent auth-loop: authenticated user visiting sign-in → redirect home
  if (isLoggedIn && (pathname.startsWith('/sign-in') || pathname.startsWith('/sign-up'))) {
    return Response.redirect(new URL('/', req.nextUrl.origin))
  }
})

export const config = {
  // Match everything except Next.js internals and static files
  matcher: ['/((?!_next/static|_next/image|favicon.ico).*)'],
}
```

### Pattern 3: TypeScript Session Augmentation

NextAuth v5 requires declaration merging to add `user.id` to the `Session` type:

```typescript
// types/next-auth.d.ts  (or root next-auth.d.ts)
// Source: https://authjs.dev/getting-started/typescript
import type { DefaultSession } from 'next-auth'

declare module 'next-auth' {
  interface Session {
    user: {
      id: string
    } & DefaultSession['user']
  }
}
```

### Pattern 5: User Registration (Custom Route)

NextAuth does not provide user registration — only sign-in. A separate API route is needed:

```typescript
// app/api/auth/register/route.ts
import { NextResponse } from 'next/server'
import bcryptjs from 'bcryptjs'
import { prisma } from '@/app/lib/prisma'

export async function POST(req: Request) {
  const { email, password, name } = await req.json()
  if (!email || !password) {
    return NextResponse.json({ error: 'Email and password required' }, { status: 400 })
  }
  const existing = await prisma.user.findUnique({ where: { email } })
  if (existing) {
    return NextResponse.json({ error: 'Email already in use' }, { status: 409 })
  }
  const hashed = await bcryptjs.hash(password, 12)
  const user = await prisma.user.create({
    data: { email, name: name ?? null, password: hashed },
  })
  return NextResponse.json({ id: user.id, email: user.email }, { status: 201 })
}
```

### Anti-Patterns to Avoid

- **Importing `auth.ts` (full Prisma config) in `middleware.ts`:** Prisma is not edge-compatible. Always import `auth.config.ts` (providers-only) in middleware. [CITED: authjs.dev/getting-started/migrating-to-v5#edge-compatibility]
- **Using `next-auth@5` install tag:** This tag does not exist on npm. Use `next-auth@beta` which resolves to 5.0.0-beta.31. [VERIFIED: npm registry]
- **Using `bcrypt` (native) instead of `bcryptjs`:** The native `bcrypt` package requires node-gyp build and fails in Railway's build environment. Use `bcryptjs` (pure JS). [ASSUMED — based on common Railway/serverless constraint]
- **Calling `signIn()` from `next-auth` (server) in a client component:** `signIn` and `signOut` for client components must come from `next-auth/react`. The server export from `@/app/lib/auth` is only for Server Components and API routes.
- **Omitting `AUTH_TRUST_HOST=true` on Railway:** Railway runs behind a reverse proxy. Without this, NextAuth v5 will reject OAuth callbacks. [CITED: authjs.dev/getting-started/deployment]
- **Setting `userId` to `null` explicitly in Prisma:** Use `userId: userId ?? undefined`. Passing `undefined` causes Prisma to skip the field entirely (leaves it NULL in DB without an explicit NULL assignment that could fail type checks).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| OAuth state + PKCE + callback handling | Custom OAuth flow | NextAuth providers | 50+ edge cases: state mismatch, token refresh, provider quirks |
| Session signing / verification | Custom JWT signing | NextAuth JWT strategy | Timing attacks, rotation, secret management |
| Password hashing | Custom hash function | `bcryptjs.hash(password, 12)` | Constant-time comparison, work factor, salt generation |
| CSRF protection on auth forms | Custom CSRF tokens | NextAuth handles automatically | NextAuth's action-token system covers this |
| OAuth account linking (same email, different provider) | Custom merge logic | PrismaAdapter handles automatically | NextAuth links accounts by email automatically |

**Key insight:** Every hand-rolled auth implementation has had critical security bugs discovered years later. NextAuth's code is reviewed by thousands; custom code is not.

## Common Pitfalls

### Pitfall 1: `next-auth@5` Does Not Exist
**What goes wrong:** `npm install next-auth@5` returns 404.
**Why it happens:** v5 is published under the `beta` dist-tag, not a `@5` semver tag.
**How to avoid:** Always install as `next-auth@beta`.
**Warning signs:** npm 404 error for `next-auth@5`.

### Pitfall 2: Importing Full Auth Config in Middleware
**What goes wrong:** Build error or runtime crash — "Module not found" or "Dynamic code evaluation not allowed in Edge Runtime".
**Why it happens:** Prisma (and `@prisma/adapter-pg`) use Node.js APIs not available in the Edge runtime where `middleware.ts` runs.
**How to avoid:** Use the split-config pattern. `middleware.ts` imports `NextAuth(authConfig)` from the providers-only `auth.config.ts`, never from `auth.ts`.
**Warning signs:** Build warnings about `crypto`, `fs`, or `net` modules in middleware bundle.

### Pitfall 3: Missing `AUTH_TRUST_HOST` on Railway
**What goes wrong:** Google OAuth callback fails with "Invalid redirect URI" or CSRF errors.
**Why it happens:** Railway puts the app behind a reverse proxy. NextAuth sees `X-Forwarded-Host` headers but rejects them unless explicitly trusted.
**How to avoid:** Set `AUTH_TRUST_HOST=true` in Railway environment variables.
**Warning signs:** OAuth works in local dev but fails in Railway production.

### Pitfall 4: `@auth/prisma-adapter` Peer Dep Gap for Prisma 7
**What goes wrong:** Peer dependency warning: `@auth/prisma-adapter` lists `>=6` as supported but not `>=7` in its peerDependencies string.
**Why it happens:** The peer dep string is `>=2.26.0 || >=3 || >=4 || >=5 || >=6` — it stops at 6. However, the adapter works with Prisma 7 in practice because it only calls standard Prisma client APIs.
**How to avoid:** Use `--legacy-peer-deps` or accept the peer dep warning. The adapter functions correctly with Prisma 7.
**Warning signs:** npm warning about unmet peer dependency during install.

### Pitfall 5: Custom Prisma Output Path Import in PrismaAdapter
**What goes wrong:** `PrismaAdapter(prisma)` receives a Prisma client generated to a custom path. This works correctly as long as the `prisma` singleton from `app/lib/prisma.ts` is passed — the adapter doesn't care where the client was generated, only that it has a valid client instance.
**How to avoid:** Pass the existing `prisma` singleton from `@/app/lib/prisma`, which already imports from the custom path `@/app/generated/prisma/client`. Do not create a second PrismaClient inside `auth.ts`.
**Warning signs:** Two PrismaClient instances in dev (hot reload issue) or conflicting connection pools.

### Pitfall 6: `NEXTAUTH_SECRET` vs `AUTH_SECRET`
**What goes wrong:** Auth fails silently in production because the wrong env var name is set.
**Why it happens:** v4 used `NEXTAUTH_SECRET`; v5 uses `AUTH_SECRET`. Both names are accepted in v5 for backward compatibility, but the CONTEXT.md refers to `NEXTAUTH_SECRET`.
**How to avoid:** Set both `AUTH_SECRET` and `NEXTAUTH_SECRET` to the same value in Railway, or use only `AUTH_SECRET`. The `.env.example` should document both.
**Warning signs:** "No secret configured" error at startup.

### Pitfall 7: bcryptjs in Edge Runtime
**What goes wrong:** `bcryptjs.compare()` or `bcryptjs.hash()` called in Edge-runtime code fails.
**Why it happens:** Even pure-JS bcryptjs uses some Node.js crypto APIs not available in Edge.
**How to avoid:** Only call bcryptjs inside `auth.ts` (the full Node.js config), never inside `auth.config.ts` (the edge config) or middleware.
**Warning signs:** Runtime error mentioning crypto in Edge context.

## Security Domain

### Applicable ASVS Categories (Level 1)

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | NextAuth v5 Credentials provider + bcryptjs (cost factor 12) |
| V3 Session Management | yes | NextAuth JWT strategy — signed HS256 JWT in httpOnly cookie |
| V4 Access Control | yes | middleware.ts + per-route `auth()` check |
| V5 Input Validation | yes | Validate email/password shape before passing to authorize; reject empty strings |
| V6 Cryptography | yes | bcryptjs.hash with cost=12; AUTH_SECRET min 32 chars; never hand-roll |

### Known Threat Patterns for Next.js Auth

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Session fixation | Elevation of Privilege | NextAuth regenerates session token on sign-in automatically |
| JWT secret exposure | Tampering | AUTH_SECRET set as Railway secret var, never in git |
| OAuth state forgery (CSRF) | Tampering | NextAuth handles state parameter automatically |
| Credential stuffing | Denial of Service | bcrypt cost factor 12 slows brute force; rate limiting out of scope Phase 3.1 |
| OAuth account takeover (email collision) | Elevation of Privilege | PrismaAdapter links accounts by email — same email from different providers merges to one User |
| Proxy host spoofing | Tampering | AUTH_TRUST_HOST=true on Railway; AUTH_SECRET signs all tokens |
