  <action>
    Four tightly related changes that complete the per-user data isolation (D-11, AUTH-03).

    --- FILE: app/lib/food.ts ---
    Modify the logMeal function signature to accept an optional userId parameter. The existing
    signature is `logMeal(description: string)`. Change it to:
    `logMeal(description: string, userId?: string | null)`

    In the prisma.meal.create call, add userId to the data object:
    ```typescript
    return prisma.meal.create({
      data: {
        description,
        userId: userId ?? undefined,  // undefined = Prisma skips field entirely (leaves DB NULL)
        foodItems: { create: foodItemsData },
      },
      include: { foodItems: true },
    })
    ```

    CRITICAL: Use `userId: userId ?? undefined` NOT `userId: userId ?? null`. Passing `undefined`
    causes Prisma to omit the field from the INSERT entirely, leaving DB NULL naturally. Passing
    `null` explicitly sets NULL and can cause TypeScript errors with the nullable FK type.
    (RESEARCH.md anti-patterns section.)

    Do NOT change extractFoodItems, NoFoodItemsError, or any other exports — only logMeal.

    --- FILE: app/api/chat/route.ts ---
    Add session reading at the top of the POST handler. Import auth from '@/app/lib/auth'.
    Read the session before the streaming ReadableStream is created:

    ```typescript
    import { auth } from '@/app/lib/auth'

    export async function POST(req: Request): Promise<Response> {
      const session = await auth()
      if (!session?.user?.id) {
        return new Response(JSON.stringify({ error: 'Unauthorized' }), {
          status: 401,
          headers: { 'Content-Type': 'application/json' },
        })
      }
      const userId = session.user.id
      // ... existing message parsing ...
      meal = await logMeal(message, userId)
    ```

    The 401 guard is intentional — middleware handles most redirects, but API routes should
    defensively re-check (RESEARCH.md Architectural Responsibility Map, route protection tier).

    The streaming structure inside ReadableStream remains unchanged. Only add:
    1. session read before the stream creation
    2. 401 guard if no session
    3. userId variable passed to logMeal(message, userId)

    --- FILE: app/api/diet/route.ts ---
    Read the file first to understand the full existing structure. Then add session filtering.

    Add `import { auth } from '@/app/lib/auth'` at the top.
    In the GET handler, read session and extract userId:
    ```typescript
    const session = await auth()
    const userId = session?.user?.id
    ```

    Add userId to the Prisma where clause. Pattern from PATTERNS.md:
    ```typescript
    where: {
      createdAt: { gte: start, lte: end },
      userId: userId ?? undefined,
    }
    ```

    When userId is undefined (unauthenticated request, which middleware should prevent but
    defensive coding), `userId: undefined` causes Prisma to skip the userId filter entirely —
    returning all meals. This is acceptable for the diet GET since middleware already blocks
    unauthenticated users from the UI, and the MCP log_food tool calls logMeal directly, not
    via HTTP.

    Do NOT add userId filtering to DailyTarget or FastingSession queries — those models do not
    have a userId FK and are out of scope for Phase 3.1 (CONTEXT.md scope fences, PATTERNS.md
    implementation notes).

    Button is already imported from '@/components/ui/button' in ChatInterface.tsx.
    signOut with callbackUrl ensures user lands on /sign-in after signing out, not a blank page.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /api/chat | Authenticated POST with session cookie; userId extracted server-side |
| browser → /api/diet | Authenticated GET; meal results filtered by session userId |
| git push → Railway | Code + Railway secrets initiate deploy; secrets never in git |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3.1-10 | Elevation of Privilege | /api/chat userId injection | mitigate | userId is ALWAYS read from server-side session via auth(), never from request body — client cannot spoof another user's meals |
| T-3.1-11 | Information Disclosure | /api/diet userId filter | mitigate | WHERE userId=session.user.id ensures users only see their own meals; unauthenticated (userId=undefined) skips filter but middleware blocks unauthenticated browser requests |
| T-3.1-12 | Tampering | AUTH_SECRET in git | mitigate | AUTH_SECRET only in .env.example as placeholder string "your-32-char-random-secret-here"; real value set only in Railway Variables |
| T-3.1-13 | Repudiation | Ownerless meals (userId=null) | accept | Existing meals have no userId per D-07 (leave existing meals as ownerless); intentional decision, not a gap |
</threat_model>
