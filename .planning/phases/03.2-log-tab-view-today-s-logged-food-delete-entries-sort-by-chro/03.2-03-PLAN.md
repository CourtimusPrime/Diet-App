## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → /api/meals/today | Client reads today's food list — server enforces auth, no client-trusted data |
| Browser → /api/meals/[mealId] DELETE | Client triggers delete — server enforces auth + ownership (handled in Plan 02) |
| Client state | Optimistic delete is client-side only; undo restores client state — server state is authoritative |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03.2-06 | Information Disclosure | TodayLog fetchToday | accept | Fetch is authenticated via session cookie forwarded automatically by browser; server enforces userId scope in Plan 02's GET /api/meals/today |
| T-03.2-07 | Tampering | Optimistic delete + undo | accept | Client state manipulation (undo) is harmless — the actual deletion is gated server-side in DELETE /api/meals/[mealId]. Restoring local state after undo does not recreate DB records; a re-fetch on next refresh will show the true DB state |
| T-03.2-08 | Elevation of Privilege | app/page.tsx | accept | auth() is called server-side; unauthenticated users receive LandingPage — no change to existing auth gate, no new surface added |
| T-03.2-09 | Denial of Service | sort pill — client sort on every tap | accept | Sort is in-memory over a bounded daily food list (typically 5–30 items); no network call on sort change; no DoS risk |
| T-03.2-SC | Tampering | npm/pip/cargo installs | accept | No new npm packages in this plan — all imports are from Plan 01/02 generated files or existing dependencies |
