## Summary

Phase 03.2 replaces the ephemeral in-memory chat stream on the Log tab (`/`) with a persistent, DB-backed list of today's food items. The core transformation is: `app/page.tsx` renders a new `LogTab` client component instead of `ChatInterface` directly; `ChatInterface` becomes a child of `LogTab` that accepts an `onMealLogged` callback; and a new `TodayLog` component fetches and displays DB-backed food cards with sort + delete.

The existing codebase is well-suited for this. `ChatInterface.tsx` already contains the `FoodCard` component and `handleSubmit` logic; both need only minor extension (new props on `FoodCard`, a callback prop on `ChatInterface`). The existing `app/api/diet/route.ts` returns meal counts and nutrient totals — it does NOT return `meals[]` with nested `foodItems[]`. A new `GET /api/meals/today` endpoint is needed to return the raw meal + foodItems structure for the log view. The `DELETE /api/meals/[mealId]` endpoint is wholly new.

Sort is confirmed to be client-side (no API cost per sort). Sonner 2.0.7 is now installed. Skeleton and Sonner shadcn components need `npx shadcn add` before implementation. The Toaster must be registered in `app/layout.tsx`.

**Primary recommendation:** Create `LogTab` as the new root component at `/`; extract `FoodCard` from `ChatInterface` into its own file; create `TodayLog` for the DB-backed list; create two new API endpoints. Sort and optimistic delete are pure client state.

### Pattern 1: New API — GET /api/meals/today

**What:** Returns today's meals with nested foodItems, scoped to authenticated user.

**When to use:** Called by `TodayLog` on mount and after each meal log.

```typescript
// app/api/meals/today/route.ts
// Source: inferred from existing app/api/diet/route.ts patterns [ASSUMED]
import { NextResponse } from 'next/server'
import { prisma } from '@/app/lib/prisma'
import { auth } from '@/app/lib/auth'

export async function GET() {
  const session = await auth()
  const userId = session?.user?.id
  if (!userId) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })

  const now = new Date()
  const start = new Date(now.toISOString().slice(0, 10) + 'T00:00:00.000Z')
  const end   = new Date(now.toISOString().slice(0, 10) + 'T23:59:59.999Z')

  const meals = await prisma.meal.findMany({
    where: { createdAt: { gte: start, lte: end }, userId },
    include: { foodItems: true },
    orderBy: { createdAt: 'desc' },   // most-recent meal first
  })

  return NextResponse.json({ meals })
}
```

**Key difference from `app/api/diet/route.ts`:** This returns `meals[]` with nested `foodItems[]`. The existing diet route only returns aggregate `totals` — it is NOT usable for rendering individual food cards.

### Pattern 2: New API — DELETE /api/meals/[mealId]

**What:** Deletes a meal by ID, cascades to foodItems (Prisma `onDelete: Cascade` already in schema).

**Auth gate:** Verify `meal.userId === session.user.id` before deleting.

```typescript
// app/api/meals/[mealId]/route.ts
// Source: Next.js App Router dynamic route patterns [ASSUMED]
import { NextResponse } from 'next/server'
import { prisma } from '@/app/lib/prisma'
import { auth } from '@/app/lib/auth'

export async function DELETE(
  _req: Request,
  { params }: { params: { mealId: string } }
) {
  const session = await auth()
  const userId = session?.user?.id
  if (!userId) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })

  const meal = await prisma.meal.findUnique({ where: { id: params.mealId } })
  if (!meal) return NextResponse.json({ error: 'Not found' }, { status: 404 })
  if (meal.userId !== userId) return NextResponse.json({ error: 'Forbidden' }, { status: 403 })

  await prisma.meal.delete({ where: { id: params.mealId } })  // cascades to foodItems
  return NextResponse.json({ ok: true })
}
```

**Schema confirmation:** `FoodItem` has `onDelete: Cascade` referencing `Meal` — verified in `prisma/schema.prisma`. [VERIFIED: codebase]

### Pattern 3: Log Refresh — Callback prop, not router.refresh()

**What:** After `ChatInterface.handleSubmit` completes, `TodayLog` re-fetches.

**Why not `router.refresh()`:** `router.refresh()` re-renders Server Components but `TodayLog` is a Client Component that manages its own fetch state. Using `router.refresh()` would re-render the whole route and lose chat input field state (textarea value). Instead, lift a `refetch` trigger into `LogTab`:

```tsx
// LogTab.tsx
'use client'
import { useState, useCallback } from 'react'
import { TodayLog } from './TodayLog'
import { ChatInterface } from './ChatInterface'

export function LogTab() {
  const [refreshKey, setRefreshKey] = useState(0)
  const triggerRefetch = useCallback(() => setRefreshKey(k => k + 1), [])

  return (
    <div className="flex flex-col h-screen bg-background">
      {/* TodayLog watches refreshKey as a useEffect dependency */}
      <TodayLog refreshKey={refreshKey} />
      <ChatInterface onMealLogged={triggerRefetch} />
    </div>
  )
}
```

`TodayLog` runs `useEffect(() => { fetchToday() }, [refreshKey])` — increment on meal logged = re-fetch. [ASSUMED: pattern based on React hooks semantics]

### Pattern 4: Optimistic Delete with Sonner Undo

**What:** Remove item from UI immediately, fire DELETE in background, show undo toast.

```tsx
// Source: sonner.emilkowal.ski/toast + shadcn Sonner docs [CITED: sonner.emilkowal.ski]
import { toast } from 'sonner'

const handleDelete = async (mealId: string) => {
  // 1. Snapshot current state for undo
  const snapshot = [...foodItems]

  // 2. Optimistic remove
  setFoodItems(prev => prev.filter(item => item.mealId !== mealId))

  // 3. Toast with Undo
  toast('Meal deleted', {
    duration: 5000,
    action: {
      label: 'Undo',
      onClick: () => {
        // Restore snapshot
        setFoodItems(snapshot)
      },
    },
  })

  // 4. Fire DELETE in background
  const res = await fetch(`/api/meals/${mealId}`, { method: 'DELETE' })
  if (!res.ok) {
    // Restore and show error
    setFoodItems(snapshot)
    toast.error("Couldn't delete meal. Please try again.")
  }
}
```

**Sonner action API (v2.0.7):** `action: { label: string, onClick: (event) => void }` [VERIFIED: npm registry + sonner.emilkowal.ski]

### Pattern 6: Client-Side Sort

**What:** Sort `FoodItem[]` in memory. Applied to the flat list of all food items across all meals.

```tsx
type SortKey = 'chronological' | 'protein_g' | 'fat_total_g' | 'carbohydrate_g' | 'fiber_g'

function sortItems(items: FoodItem[], sort: SortKey): FoodItem[] {
  if (sort === 'chronological') {
    // Items are already ordered by meal.createdAt desc, item order within meal
    return items
  }
  return [...items].sort((a, b) => {
    const av = (a[sort] as number | null) ?? -Infinity
    const bv = (b[sort] as number | null) ?? -Infinity
    return bv - av  // descending: highest value first, nulls last
  })
}
```

**Data shape:** After `GET /api/meals/today` returns `meals[]`, flatten to `FoodItem[]` on the client:
```ts
const items = meals.flatMap(meal =>
  meal.foodItems.map(item => ({ ...item, mealId: meal.id }))
)
```

**Chronological order:** `GET /api/meals/today` uses `orderBy: { createdAt: 'desc' }` (most recent meal first). Items within each meal are returned in DB insertion order. The flat map preserves this ordering. No re-sort needed for chronological — the `items` array is already in the right order.

### Anti-Patterns to Avoid

- **Putting `FoodCard` logic in two places:** Extract to `components/FoodCard.tsx` before the phase starts — don't duplicate it in `TodayLog`.
- **Using `router.refresh()` for list refresh:** It re-renders the server component and can reset form state. Use the `refreshKey` callback pattern instead.
- **Awaiting DELETE before removing from UI:** Makes delete feel slow (600ms+ round trip). Always remove optimistically first.
- **Re-fetching on every sort change:** Sort is client-side. Only fetch on mount and after `onMealLogged`. Never fetch on sort pill tap.
- **Calling `/api/diet` for the log list:** The diet endpoint returns aggregate totals only, not individual food items. It requires a `?date=` query param and was designed for the Diet tab totals view.
- **Forgetting to add `<Toaster />` to layout:** Sonner toasts are invisible without a `<Toaster />` mounted in the tree. Must be added to `app/layout.tsx`.
- **Timezone mismatch in date scoping:** The existing diet route uses UTC boundaries (`T00:00:00.000Z`). The new meals/today route should match this. If the user is in a non-UTC timezone, "today" in UTC may not match local midnight. For a personal app this is acceptable for now (deferred — CONTEXT.md confirms no date picker scope).

## Common Pitfalls

### Pitfall 1: `/api/diet` Returns Totals, Not Food Cards
**What goes wrong:** Developer calls `GET /api/diet` expecting `meals[]` with `foodItems[]`, gets aggregate totals only.
**Why it happens:** The existing route was built for the Diet tab's nutrition dashboard, not for rendering individual FoodCard components.
**How to avoid:** Create `GET /api/meals/today` returning `{ meals: Meal[] }` with `include: { foodItems: true }`.
**Warning signs:** The response contains a `totals` key — wrong endpoint.

### Pitfall 2: Sonner Toaster Not Mounted
**What goes wrong:** `toast()` is called but nothing appears on screen. No error in console.
**Why it happens:** `sonner` requires a `<Toaster />` component mounted in the React tree.
**How to avoid:** Add `<Toaster />` (from `@/components/ui/sonner`) to `app/layout.tsx` inside `<Providers>` (or alongside `<BottomNav />`).
**Warning signs:** `toast()` calls execute without any visible notification.

### Pitfall 3: Undo Tap After DELETE Resolves
**What goes wrong:** User taps Undo after the DELETE has already committed; UI restores cards but DB has no meal.
**Why it happens:** The 5-second undo window overlaps with the DELETE round-trip (typically 200-600ms).
**How to avoid:** Track the DELETE promise. If Undo is tapped before the DELETE resolves, cancel conceptually (show restored state). If Undo is tapped after DELETE resolves, trigger a `GET /api/meals/today` re-fetch to confirm actual DB state. The UI-SPEC permits a simple soft-restore of local state if DELETE hasn't resolved yet.
**Warning signs:** Cards reappear after Undo but disappear again on next page refresh.

### Pitfall 4: FoodCard mealId Confusion
**What goes wrong:** Multiple food items in one meal all have the same `mealId`; tapping any trash icon deletes the entire meal (correct), but in the flat list view it's not obvious which cards will disappear together.
**Why it happens:** Sort flattens items cross-meal; visual grouping is absent (no meal dividers per UI-SPEC).
**How to avoid:** This is intentional per CONTEXT.md ("No visual meal-group dividers"). Ensure the DELETE call uses the `mealId` from the item, and the optimistic filter is `items.filter(i => i.mealId !== deletedMealId)` — removes ALL items with that mealId.

### Pitfall 5: ChatInterface Textarea State Reset
**What goes wrong:** After a meal is logged, the textarea clears and then the page appears to reset because `router.refresh()` was used.
**Why it happens:** `router.refresh()` causes server component re-render which can reset client component state including the chat input.
**How to avoid:** Use the `refreshKey` / `onMealLogged` callback pattern. `ChatInterface` calls `onMealLogged()` after `handleSubmit` succeeds; `LogTab` increments `refreshKey`; `TodayLog` re-fetches. `ChatInterface` input state is untouched.

### Pitfall 6: Sort Nulls Handling
**What goes wrong:** Items with `null` nutrient values sort to the top when sorted by nutrient.
**Why it happens:** `null ?? 0` sorts nulls equal to zero, not last.
**How to avoid:** Use `null ?? -Infinity` for descending sort — nulls go to the bottom.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| IDOR — delete another user's meal | Tampering | Verify `meal.userId === session.user.id` before `prisma.meal.delete` |
| Unauthenticated DELETE | Elevation of Privilege | Return 401 if `!userId` before any DB operation |
| Missing auth on GET /api/meals/today | Info Disclosure | Return 401 if `!userId` — only return meals for authenticated user |

**Critical note for DELETE route:** The Prisma schema allows `userId: null` on old Meal rows (pre-auth). The DELETE route must handle the case where `meal.userId === null` — these should be treated as inaccessible to any authenticated user (return 403) to prevent orphan meal deletion by any logged-in user.
