# Phase 03.2: Code Review Report

**Reviewed:** 2026-06-03
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

The phase delivers a working Log Tab with today's food list, sort pills, and optimistic delete with
Undo toast. The DELETE route's IDOR guard and null-userId orphan check are correctly implemented.
The `refreshKey` pattern for triggering re-fetches without resetting chat input state is sound in
principle.

However, there are three blockers: the Undo toast does not actually prevent the server-side delete,
meaning clicking Undo after the DELETE completes silently lies to the user (record is gone from the
DB); the `handleDelete` async function is missing a top-level try/catch, so network errors produce
unhandled promise rejections; and concurrent rapid deletes cause snapshot-based state to corrupt
because each deletion closes over the in-flight optimistic state rather than the committed state.
There are also four warnings covering a stale UTC-only date window, a double `h-screen` layout
conflict, a misleading `sticky top-14` offset, and an unsafe cast in the fiber sort path.

## Critical Issues

### CR-01: Undo toast does not abort the server DELETE — data loss after Undo

**File:** `components/TodayLog.tsx:96-110`

**Issue:** The toast is shown and the DELETE fetch is fired sequentially in the same async function,
with no abort mechanism. The DELETE request completes in ~200 ms (typical Railway round-trip); the
Undo button window is 5 000 ms. After `fetch(...)` returns `ok`, clicking Undo calls
`setFoodItems(snapshot)` — restoring the item in the UI — but the record is already gone from the
database. The user sees a restored card that will vanish on the next refresh or page reload. This is
silent data loss.

**Fix:** Issue an `AbortController` signal to the fetch. If Undo is clicked before the fetch
completes, abort it. If the fetch has already completed successfully, the Undo action must
re-create the meal on the server (a POST to a restore endpoint, or re-fetch to reconcile). The
minimum safe fix is to fire the DELETE only after the 5-second toast window closes (if Undo was not
clicked), and abort if Undo was clicked:

```typescript
const handleDelete = (mealId: string) => {
  const snapshot = [...foodItems]
  setFoodItems((prev) => prev.filter((i) => i.mealId !== mealId))

  let undone = false
  toast('Meal deleted', {
    duration: 5000,
    action: {
      label: 'Undo',
      onClick: () => {
        undone = true
        setFoodItems(snapshot)
      },
    },
    onAutoClose: async () => {
      if (undone) return
      const res = await fetch(`/api/meals/${mealId}`, { method: 'DELETE' })
      if (!res.ok) {
        setFoodItems(snapshot)
        toast.error("Couldn't delete meal. Please try again.")
      }
    },
  })
}
```

Note: Sonner's `onAutoClose` callback fires when the toast expires without being dismissed via
action. This pattern defers the destructive network call until after the Undo window closes.

### CR-02: `handleDelete` has no try/catch — unhandled promise rejection on network error

**File:** `components/TodayLog.tsx:96-110`

**Issue:** `handleDelete` is an `async` function. The `fetch(...)` call inside it can throw
(network unavailable, CORS error, etc.) with no surrounding try/catch. The call site in FoodCard
(`onClick={() => onDelete(mealId)}`) discards the returned Promise because `onDelete` is typed as
`(mealId: string) => void`. TypeScript does not flag this. A network throw produces an unhandled
promise rejection: the UI freezes in the optimistically-deleted state with no error toast and no
snapshot restore.

**Fix:** Wrap the fetch and state restoration logic in a try/catch:

```typescript
const handleDelete = async (mealId: string) => {
  const snapshot = [...foodItems]
  setFoodItems((prev) => prev.filter((i) => i.mealId !== mealId))
  // ... show toast ...
  try {
    const res = await fetch(`/api/meals/${mealId}`, { method: 'DELETE' })
    if (!res.ok) {
      setFoodItems(snapshot)
      toast.error("Couldn't delete meal. Please try again.")
    }
  } catch {
    setFoodItems(snapshot)
    toast.error("Couldn't delete meal. Check your connection.")
  }
}
```

Separately, update the `onDelete` prop type in `FoodCard.tsx` to accurately reflect the async
nature:

```typescript
onDelete?: (mealId: string) => void | Promise<void>
```

### CR-03: Concurrent rapid deletes corrupt UI state via stale snapshots

**File:** `components/TodayLog.tsx:97-108`

**Issue:** Each call to `handleDelete` captures `snapshot = [...foodItems]` at the moment of
invocation. If the user deletes meal A and then quickly deletes meal B before A's DELETE completes:

- snapshot\_A = `[A, B, C]`, items become `[B, C]`
- snapshot\_B = `[B, C]` (taken after A was optimistically removed), items become `[C]`
- If DELETE A fails: `setFoodItems(snapshot_A)` → `[A, B, C]` — but B has already been
  deleted in the DB. UI now shows B which is gone server-side.
- If DELETE B fails: `setFoodItems(snapshot_B)` → `[B, C]` — A is missing from the snapshot,
  so A's UI card is lost even though DELETE A might have failed.

Either failure path leaves UI and DB out of sync permanently (until manual refresh).

**Fix:** The safest fix is to re-fetch from the server on any DELETE failure rather than restoring
a stale snapshot:

```typescript
if (!res.ok) {
  await fetchToday()          // authoritative reconciliation
  toast.error("Couldn't delete meal. Please try again.")
}
```

If deferred-delete (CR-01 fix) is adopted, the multi-delete problem is reduced since only one
in-flight delete would exist per toast window.

## Warnings

### WR-01: UTC-only date window excludes valid same-day meals for non-UTC users

**File:** `app/api/meals/today/route.ts:10-12`

**Issue:** The query window is built from the server's UTC date:

```typescript
const today = new Date().toISOString().slice(0, 10)  // UTC date
const start = new Date(`${today}T00:00:00.000Z`)
const end   = new Date(`${today}T23:59:59.999Z`)
```

A user in UTC+10 logging a meal at 1:00 AM local time is at 15:00 UTC yesterday. That meal's
`createdAt` is in yesterday's UTC window, so it will not appear in today's log. Conversely, a user
in UTC-8 will see meals logged after midnight local time (which are in tomorrow's UTC window)
disappear from today's view.

The `end` bound also has a sub-millisecond gap: PostgreSQL stores timestamps with microsecond
precision. A record at `23:59:59.9991Z` is greater than the `end` value of `23:59:59.999Z` and
would be excluded. Use an exclusive upper bound instead:

**Fix:**
```typescript
const start = new Date(`${today}T00:00:00.000Z`)
const end   = new Date(start.getTime() + 24 * 60 * 60 * 1000)  // exclusive midnight tomorrow UTC

const meals = await prisma.meal.findMany({
  where: { createdAt: { gte: start, lt: end }, userId },
  ...
})
```

For proper timezone support, accept a `tz` query parameter from the client and derive the local
day's UTC window server-side using a library such as `date-fns-tz`.

### WR-02: `ChatInterface` renders a second `h-screen` root inside `LogTab`'s `h-screen`

**File:** `components/ChatInterface.tsx:151`, `components/LogTab.tsx:12`

**Issue:** `LogTab` wraps its children in `<div className="flex flex-col h-screen">`. `TodayLog`
correctly uses `flex-1 min-h-0 overflow-hidden` to fit within that container. But `ChatInterface`
(rendered second inside the same flex column) starts with its own `<div className="flex flex-col
h-screen">`, making it 100 vh tall on its own. This nests two `h-screen` elements inside a single
viewport column, causing `ChatInterface` to overflow below the fold. The inner scroll area and the
fixed input bar will be positioned incorrectly.

`ChatInterface` was originally written as a standalone full-page component (confirmed by the
worktree snapshot at `.claude/worktrees/`). It was composed into `LogTab` without removing or
parameterising its self-contained layout wrapper.

**Fix:** Remove the `h-screen` wrapper from `ChatInterface` and make it a flex child:

```tsx
// ChatInterface.tsx — change root div
<div className="flex flex-col flex-1 min-h-0 overflow-hidden bg-background">
```

The fixed input bar (`bottom-16`) should become `sticky bottom-0` or be hoisted to the `LogTab`
level if the layout requires it.

### WR-03: Sort bar `sticky top-14` offset has nothing above it in `LogTab`

**File:** `components/TodayLog.tsx:118`

**Issue:** The sort pill row uses `sticky top-14` (56 px from the top). In the `LogTab` layout,
`TodayLog` renders first — at the very top of the viewport. There is no 56 px element above it
(the `ChatInterface` NutriLog header is rendered below `TodayLog`, not above). The sort bar will
therefore stick 56 px below the viewport edge during scroll, leaving a gap at the top rather than
pinning flush to the top of the visible area.

The `top-14` was presumably written to clear the `ChatInterface` header (`h-14`), but the render
order in `LogTab` places the header below the log, not above it.

**Fix:** Either re-order the components in `LogTab` (header/chat input above, log below) or change
the sort bar sticky offset to `top-0` if `TodayLog` is always at the top of the scroll container.

### WR-04: `fiber_g` sort cast is unsafe — `fiber_g` absent from explicit `FoodItem` interface

**File:** `components/TodayLog.tsx:39`, `components/FoodCard.tsx:16-27`

**Issue:** `FoodItem` explicitly declares four numeric fields (`energy_kcal`, `protein_g`,
`carbohydrate_g`, `fat_total_g`) plus an index signature `[key: string]: unknown`. The sort in
`TodayLog` casts `a[sort]` to `number | null`:

```typescript
const av = (a[sort] as number | null) ?? -Infinity
```

When `sort === 'fiber_g'`, this is a `as` cast on an `unknown` value from the index signature. If
the API ever returns `fiber_g` as a string or omits it entirely (and it's not in the interface
contract), the arithmetic `bv - av` silently produces `NaN`, which breaks the sort (all comparisons
return `false`, causing undefined sort order). TypeScript does not catch this because the cast is
explicit.

**Fix:** Add `fiber_g` to the `FoodItem` interface with the correct type:

```typescript
export interface FoodItem {
  // ... existing fields ...
  fiber_g: number | null
  [key: string]: unknown
}
```

And add a runtime guard in `sortItems`:

```typescript
const av = typeof a[sort] === 'number' ? (a[sort] as number) : -Infinity
const bv = typeof b[sort] === 'number' ? (b[sort] as number) : -Infinity
```

## Info

### IN-01: `chronological` sort shows newest-first, which contradicts the label

**File:** `components/TodayLog.tsx:37`, `app/api/meals/today/route.ts:17`

**Issue:** The API returns meals ordered by `createdAt: 'desc'` (newest first). `TodayLog` flattens
`meal.foodItems` in that order. The `chronological` sort option is a no-op (`return items`) so it
preserves the newest-first API order. Users typically expect "chronological" to mean oldest-first
(time-ordered forward). The reverse ordering may be intentional for a "latest at top" UX, but the
label is misleading.

**Fix:** Either rename the option to `'Recent first'` / `'Latest'`, or change the API query to
`orderBy: { createdAt: 'asc' }` and invert the default sort pill to match.

### IN-02: `labelFromKey` produces lowercase interior words for nutrient display labels

**File:** `components/FoodCard.tsx:58-61`

**Issue:** `labelFromKey` converts `vitamin_c_mg` to `'Vitamin c mg'` — only the first character
is capitalised and the unit suffix is left in the label text (making it redundant with the value
column). The result in the expanded nutrient list reads awkwardly: `"Vitamin c mg  0.00 mg"`.

**Fix:** Strip the unit suffix from the label and use title-case conversion:

```typescript
function labelFromKey(key: string): string {
  // Strip known unit suffixes before display
  const stripped = key.replace(/_(mcg|mg|kcal|g)$/, '')
  return stripped
    .split('_')
    .map((w) => w.charAt(0).toUpperCase() + w.slice(1))
    .join(' ')
}
```
