<task type="checkpoint:human-action">
  <name>Task 1: Set env vars in Railway dashboard and trigger deploy</name>
  <what-to-do>
    1. Go to https://railway.app → nutrilog project → your service → Variables tab.

    2. Add the following environment variables:

       DATABASE_URL
       - Copy the full value from your local .env file.
       - It starts with: postgresql://...@zephyr.proxy.rlwy.net:29839/...
       - IMPORTANT: The database is in a DIFFERENT Railway project. Do NOT use a Railway
         reference variable like ${{Postgres.DATABASE_URL}} — that only works for services in
         the SAME project. Set the raw external proxy URL directly.

       OPENROUTER_API_KEY
       - Your OpenRouter API key from openrouter.ai/keys
       - Required — the app will fail to parse meals without this.

       USDA_API_KEY
       - Optional. If you have a key from api.data.gov, add it here.
       - If omitted, the app falls back to DEMO_KEY (30 req/hr limit — fine for smoke testing).

    3. After all three vars are set, go to the Deployments tab and click "Deploy" (or push a
       commit to trigger auto-deploy if GitHub integration is connected).

    4. Watch the deployment logs. Expected sequence:
       - "Installing dependencies..." (npm install)
       - "Running build command: npm run build"
         - "prisma generate" completes first
         - "next build" compiles the app
       - "Build succeeded"
       - "Starting service..."
       - App logs show "Ready on http://..." with the PORT Railway injected

    5. If the build fails: paste the last 20 lines of the build log here for diagnosis.
       Common failures and fixes:
       - "bun.lock: InvalidLockfileVersion" → packageManager field not saved in package.json
         (re-check Plan 01 Task 1 was committed and pushed)
       - "Cannot find module '../generated/prisma/client'" → prisma generate did not run;
         verify build script in package.json is still `prisma generate && next build`
       - "Application failed to respond" after deploy → PORT flag missing from start script;
         re-check Plan 01 Task 1
  </what-to-do>
  <resume-signal>
    Type "deployed" and paste the Railway app URL (e.g. https://nutrilog-production.up.railway.app)
    once the deployment log shows "Build succeeded" and the health check passes.
  </resume-signal>
</task>

<task type="checkpoint:human-verify">
  <name>Task 2: Verify live app and log a test meal</name>
  <what-built>
    Railway has deployed the NutriLog Next.js app. Database connectivity and the full
    meal-logging pipeline need to be confirmed end-to-end against the live URL.
  </what-built>
  <how-to-verify>
    1. Open the Railway app URL in your browser (the *.railway.app URL from Task 1).
       Expected: NutriLog chat interface loads. You should see the chat input field.

    2. Type a test meal and send it:
       "I had a chicken breast and a cup of brown rice for lunch"

       Expected: After a few seconds, food cards appear — one for chicken breast and one for
       brown rice. Each card shows kcal and macro values.

    3. Confirm the records hit the database. In a local terminal:
       The MCP server still points to the same Railway PostgreSQL database. Run:
       ```
       bun mcp/server.ts
       ```
       Then in a new terminal, call get_meals via the MCP CLI or check directly:
       ```
       psql "$DATABASE_URL" -c "SELECT id, created_at FROM \"Meal\" ORDER BY created_at DESC LIMIT 3;"
       ```
       Expected: A new Meal row appears with a timestamp from the last few minutes.

    4. Check that the food cards show macros (not all zeros / empty):
       - energy_kcal should be non-zero for chicken breast
       - protein_g should be non-zero

    If any step fails: report which step and what error appeared.
  </how-to-verify>
  <resume-signal>
    Type "verified" if the meal logged and macros appeared. Describe any issues if not.
  </resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Railway app (*.railway.app) | Public HTTPS endpoint; user input crosses into LLM parsing pipeline |
| Railway app → OpenRouter API | OPENROUTER_API_KEY leaves Railway container to external LLM provider |
| Railway app → Railway PostgreSQL (separate project) | DATABASE_URL uses external proxy URL; traffic crosses Railway's public network |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-03 | Information Disclosure | DATABASE_URL in Railway env vars | mitigate | Set via Railway dashboard Variables tab (encrypted at rest); never commit to git |
| T-03-04 | Information Disclosure | OPENROUTER_API_KEY in Railway env vars | mitigate | Same — Railway dashboard only; not in railway.json or any committed file |
| T-03-05 | Denial of Service | External proxy DATABASE_URL latency | accept | Single-user personal app; cross-project egress acceptable for Phase 3 |
| T-03-06 | Spoofing | Open chat endpoint at Railway URL | accept | Personal app with no auth in Phase 3; auth added in Phase 3.1 |
| T-03-SC | Tampering | npm/pip/cargo installs | accept | No new packages in this phase |
</threat_model>
