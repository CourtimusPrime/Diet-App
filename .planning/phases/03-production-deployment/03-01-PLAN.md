<task type="auto">
  <name>Task 1: Fix package.json — PORT flag and packageManager field</name>
  <files>package.json</files>
  <action>
    Make two targeted edits to package.json:

    1. Change the "start" script from `"next start"` to `"next start -p ${PORT:-3000}"`.
       Railway injects a PORT env var. Next.js 14's `next start` does NOT auto-read PORT — it must
       be passed via the -p flag. Without this fix, the app binds to 3000 and Railway routes to a
       different port, producing a 502 "Application failed to respond" error on every request.
       The fallback `:-3000` keeps local `npm run start` working without a PORT env var set.

    2. Add `"packageManager": "npm@10.9.7"` as a top-level field in package.json (alongside
       "name", "version", etc.). The repo has a bun.lock (text format, Bun v1.2+). nixpacks on
       Railway may be on a version older than v1.31.0, which throws `InvalidLockfileVersion` when
       it encounters bun.lock's text format. The packageManager field tells nixpacks to use npm,
       bypassing lockfile detection entirely. This field does not affect local development.

    Do NOT change any other scripts. The "build" script (`prisma generate && next build`) is
    correct as-is — prisma generate must run before next build in the same command.
  </action>
  <verify>
    <automated>node -e "const p = require('./package.json'); const s = p.scripts.start; const pm = p.packageManager; if (!s.includes('-p')) { process.exit(1); } if (!pm || !pm.startsWith('npm')) { process.exit(1); } console.log('start:', s); console.log('packageManager:', pm);"</automated>
  </verify>
  <done>
    package.json scripts.start is `"next start -p ${PORT:-3000}"` and packageManager is
    `"npm@10.9.7"`. All other scripts are unchanged.
  </done>
</task>

<task type="auto">
  <name>Task 2: Create railway.json deploy config</name>
  <files>railway.json</files>
  <action>
    Create railway.json at the project root with the following content. This file pins the build
    and start commands explicitly so Railway does not guess them from nixpacks heuristics. Both
    commands delegate to the package.json scripts — package.json remains the single source of
    truth for what runs.

    Fields:
    - build.builder: "NIXPACKS" — use nixpacks (Railway default, explicit here for clarity)
    - build.buildCommand: "npm run build" — runs `prisma generate && next build`
    - deploy.startCommand: "npm run start" — runs `next start -p ${PORT:-3000}` (after Task 1 fix)
    - deploy.restartPolicyType: "ON_FAILURE" — restart the container if it crashes
    - deploy.restartPolicyMaxRetries: 3 — prevent infinite restart loops on hard failures

    Include the Railway JSON schema reference as the $schema field for dashboard validation.

    Note: The exact railway.json schema field names (buildCommand, startCommand,
    restartPolicyType) come from the Railway build configuration docs. If the Railway dashboard
    JSON editor shows schema errors after the project is created, consult the dashboard's
    inline error hints and adjust field names. The logic above is correct regardless of exact
    key names.
  </action>
  <verify>
    <automated>node -e "const r = require('./railway.json'); if (r.build.builder !== 'NIXPACKS') process.exit(1); if (!r.deploy.startCommand.includes('npm run start')) process.exit(1); console.log('railway.json valid:', JSON.stringify(r, null, 2));"</automated>
  </verify>
  <done>
    railway.json exists at project root with NIXPACKS builder, buildCommand "npm run build",
    startCommand "npm run start", and restart policy set.
  </done>
</task>
